# Divergence from upstream

Everything this repo changes relative to [jellyfin/jellyfin](https://github.com/jellyfin/jellyfin) at the ref pinned in `UPSTREAM_REF`. The list is the contract: if it's not here, we didn't change it.

Measured 17.90ms -> 2.52ms per count (independently 2.87ms -> 0.50ms, 447 -> 65 buffers) with identical results across all 184 series; this was the most expensive statement in the database, 10,025s over 2.7M calls. Upstream bug, not multi-replica-specific | upstream stops counting the materialised grouping (report/PR filed) |
| `0009-items-search-plain-terms-with-LIKE-so-a-trigram-inde.patch` | search and NameContains plain-term branches use `EF.Functions.Like` instead of `string.Contains`, which Npgsql emits as `strpos()`; the LIKE form is served by the trigram GIN indexes the jellyfin-pgsql provider ensures on `CleanName` / `lower(OriginalTitle)`. Measured 0.93s alone / 4.8s p50 at 20 concurrent as sequential scans before | upstream searches with a pattern predicate or an index-aware operator (report/PR filed) |
| `0010-items-latest-read-the-date-cutoff-before-the-item-qu.patch` | `GetLatestItemList` reads the top-N `DateCreated` cutoff as its own statement and filters the item query on the value instead of inlining the scalar subquery. Same rows and order by construction; an empty cutoff returns empty, as `>= NULL` did. Measured 130-139ms / 62,796 buffers + 1,813 temp -> 59-78ms / 46,260 buffers for a Limit=16 TV row; the two Latest shapes were 264s/day of DB time and sit behind every home-screen Latest row. Upstream bug, not multi-replica-specific | upstream rewrote this path (PR #16062 returns Season/Series containers, a different API result); drop when UPSTREAM_REF contains it and the clients are happy with the new shape |
| `0011-items-count-a-season-s-children-instead-of-materiali.patch` | `Season.GetItemsInternal` answers the `Limit=0` count shape (what `Folder.FillUserDataDtoValues` issues per Season DTO) with the repository count instead of fetching every episode of the whole series plus every user's UserData and filtering in memory. New `InternalItemsQuery.SeasonMembership` (SQL form of `FilterEpisodesBySeason`: `ParentIndexNumber = N` or `SeasonId` points at a same-key Season) and `HasAiredSeasonOverride` (a LIKE on the Data blob; any series carrying AirsBefore/After keeps the in-memory path, exact because Data omits nulls); `Folder.RequiresPostFiltering` becomes protected. Revisit only if a client stalls on a 1-entry playlist | upstream still waits for the requested minimum; drop if upstream adds its own fast-start |
| `0013-tv-probe-the-next-up-candidates-in-parallel.patch` | `TVSeriesManager.GetNextUpEpisodes` runs the per-series last-watched probe through ordered PLINQ (degree <= 8) instead of sequentially: ~20 candidate series x 2-3 statements dominated the home screen's NextUp call (1.27s of a 3.5s load, 2026-08-31). | `0015-startup-raise-the-thread-pool-worker-floor-in-code.patch` | `StartApp` raises the managed thread-pool worker floor to max(32, current) in code and logs the before/after values at Information; grep the pod's startup log for `Thread pool worker floor raised` to prove the floor is real (a Warning line replaces it if the runtime refuses), and tests/smoke.sh asserts the line on both serving pods. The env knob was deployed and silently ignored: `DOTNET_ThreadPool_MinThreads=32` left the floor at the core count (the `DOTNET_`/`COMPlus_` family gives no feedback and also hex-parses numbers), so bursts of synchronous cache writes starved the pool, API p95 hit 4.6-5.1s and webOS clients timed out (2026-08-27). 32 from the 2026-08-29 load measurement (homelab-kubernetes 1cd5ba7d); completion-port floor untouched; runs in every startup mode including the migration Job | upstream or the runtime raises the default floor, or the runtime makes the env knob reliable and observable; the `DOTNET_ThreadPool_MinThreads` env in homelab-kubernetes becomes redundant (not harmful, code takes the max) the moment this ships |
| `0016-userdata-upsert-saves-so-duplicate-reports-cannot-ra.patch` | `UserDataManager.SaveUserData` writes UserData through `INSERT ... ON CONFLICT ("ItemId", "UserId", "CustomDataKey") DO UPDATE` instead of exists-check then Add/Attach: duplicate client progress/stop reports raced the check into INSERT vs INSERT and the loser aborted on `PK_UserData` (Postgres 23505 -> `DbUpdateException` -> HTTP 500 on `POST /Sessions/Playing/Progress`). DO UPDATE overwrites every non-key column, exactly what Attach+Modified did, so single-writer behavior is unchanged; the same statement is valid SQLite (3.24+). Errors now surface per-statement as the provider's `DbException` instead of a `DbUpdateException` at SaveChanges; one round-trip per user-data key (typically 1-2, shortcut: note in the code) | upstream makes `SaveUserData` conflict-safe |
| `0017-items-upsert-provider-rows-so-parallel-saves-cannot-.patch` | `UpdateOrInsertItems` writes an existing item's `BaseItemProviders` rows through `INSERT ... ON CONFLICT ("ItemId", "ProviderId") DO UPDATE` instead of riding the re-attached change tracker: two parallel saves of the same item both run the provider `ExecuteDelete`, neither DELETE sees the other's uncommitted re-inserts under READ COMMITTED, and the losing transaction aborted on `PK_BaseItemProviders` (4x in one library-scan window). Rows are upserted in ordinal ProviderId order so concurrent transactions take row locks in one sequence (no 40P01 deadlock window). Same treatment as 0003's ItemValues get-or-create; new-item inserts are untouched (a race there hits `PK_BaseItems` first, a different failure). Known residual: the sibling delete-then-reinsert paths (BaseItemImageInfos, BaseItemMetadataFields) stay on the tracker; their per-row Guids cannot collide across transactions, but the same race can duplicate rows there | upstream serialises or upserts provider writes (same ItemPersistenceService refactor line as 0003) |
| `0018-startup-redact-credential-bearing-values-from-the-en.patch` | `LogEnvironmentInfo` prints the startup env dump with the VALUE replaced by `[redacted]` for any variable whose name contains `SECRET`, `PASSWORD`, `TOKEN`, `APIKEY`, or `API_KEY` (case-insensitive); the name still prints, so the dump keeps proving which knobs are set. Defense in depth: the acute leak (a secretKeyRef named `JELLYFIN_SSO_CLIENT_SECRET` printed into the pod log, the aggregator, and every support bundle) is removed manifest-side, this kills the class for any future credential-bearing env var | upstream redacts its own environment dump |

Image-layer divergence (no server patch involved):

| Layer | What | Drop when |
|---|---|---|
| rffmpeg dispatch shims | [rffmpeg](https://github.com/joshuaboniface/rffmpeg) pinned by commit + checksum (no upstream releases), installed as `ffmpeg-dispatch`/`ffprobe-dispatch` with a baked `/etc/rffmpeg/rffmpeg.yml`; routes encodes to an ssh worker with local fallback | Jellyfin grows native remote transcoding |

Ceilings worth knowing:

- Single-node behavior is unchanged by construction: every gate defaults open when `JELLYFIN_ROLE` is unset, the skip-gate only acts when its env var is set, and the dispatch shims sit unused until the encoder path is pointed at them. A stock deployment of this image behaves like the official one.
- The image build compiles the server but keeps the official image's jellyfin-web and jellyfin-ffmpeg; a web or ffmpeg change upstream arrives via the base image bump, not this repo.
- The dispatch path is single-worker with local fallback, not worker HA: rffmpeg load-balances across registered hosts, but this repo's smoke only proves one worker plus fallback. Register more hosts if you need spread.
- Builds carry `-p:NoWarn=CA1707` until UPSTREAM_REF passes upstream's own rename of two migration class names (same story as the sibling plugin repo).
