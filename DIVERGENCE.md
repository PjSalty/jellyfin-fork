# Divergence from upstream

Everything this repo changes relative to [jellyfin/jellyfin](https://github.com/jellyfin/jellyfin) at the ref pinned in `UPSTREAM_REF`. The list is the contract: if it's not here, we didn't change it.

| Patch | What | Drop when |
|---|---|---|
| `0001-startup-backport-the-MigrateSystem-and-SeedSystem-mo.patch` | backport of upstream PR 16319: `--mode MigrateSystem\|SeedSystem` run-and-exit modes, the hook for a single-writer migration Job | UPSTREAM_REF moves to a base containing PR 16319 |
| `0002-migrations-skip-gate-for-replica-processes.patch` | migration skip-gate: `JELLYFIN_SKIP_MIGRATIONS=true` fails fast on pending migrations instead of racing N replicas through them | upstream grows an equivalent |
| `0003-items-make-the-ItemValues-get-or-create-concurrency-.patch` | port of upstream PR 17119: ItemValues get-or-create made concurrency-safe under parallel item saves | UPSTREAM_REF contains PR 17119 (lands in the ItemPersistenceService refactor line) |
| `0004-replication-leader-gate-background-work.patch` | leader gating: scheduled task triggers, trigger-originated scans, and LiveTV/DVR timer arming run only where `JELLYFIN_ROLE` is unset or `leader` | upstream ships first-class multi-instance roles |
| `0005-devices-read-through-to-the-database-on-token-cache-.patch` | device token read-through: token cache misses re-check the database before rejecting, so tokens minted by another replica work | upstream makes the token path DB-backed |
| `patches/0007-users-split-the-user-query.patch` | `UserQuery` uses `AsSplitQuery` so the three sibling collections stop returning a cartesian product (~312 rows per user load). Measured 12.13ms -> 2.27ms and 70.2ms -> 4.36ms; these were the #1 and #2 queries by cumulative DB time | upstream switches to a split query |
| `0006-users-delete-permissions-and-preferences-on-update-in.patch` | `UpdateUserAsync` deletes the user's old Permissions/Preferences instead of orphaning them. `Permission.UserId` is `Guid?` (optional), so `Clear()` makes EF *sever* (`SET "UserId" = NULL`) rather than delete; every call stranded 24+13 unreachable rows. Upstream bug, not multi-replica-specific: SQLite installs leak the same rows | upstream fixes it (report/PR filed) |
| `0008-items-count-the-grouping-instead-of-materialising-it.patch` | `GetItems` counts the distinct grouping keys rather than counting the grouped-and-re-rooted query, and returns early when `Limit=0`. `Folder.FillUserDataDtoValues` runs a `Limit=0` count per folder to fill `UnplayedItemCount`, so a 100-series grid paid 100 counts plus 100 item queries that can only return nothing. Measured 17.90ms -> 2.52ms per count (independently 2.87ms -> 0.50ms, 447 -> 65 buffers) with identical results across all 184 series; this was the most expensive statement in the database, 10,025s over 2.7M calls. Upstream bug, not multi-replica-specific | upstream stops counting the materialised grouping (report/PR filed) |
| `0009-items-search-plain-terms-with-LIKE-so-a-trigram-inde.patch` | search and NameContains plain-term branches use `EF.Functions.Like` instead of `string.Contains`, which Npgsql emits as `strpos()`; the LIKE form is served by the trigram GIN indexes the jellyfin-pgsql provider ensures on `CleanName` / `lower(OriginalTitle)`. Same rows by construction (the wildcard check selects these branches only for metacharacter-free terms). Measured 0.93s alone / 4.8s p50 at 20 concurrent as sequential scans before | upstream searches with a pattern predicate or an index-aware operator (report/PR filed) |
| `0010-items-latest-read-the-date-cutoff-before-the-item-qu.patch` | `GetLatestItemList` reads the top-N `DateCreated` cutoff as its own statement and filters the item query on the value instead of inlining the scalar subquery. Inlined, `ApplyGroupingFilter` duplicated the WHERE (and with it the top-N scan and its per-row UserData SubPlan) into both the representative subquery and the group scan, and the plan spilled to temp. Same rows and order by construction; an empty cutoff returns empty, as `>= NULL` did. Measured 130-139ms / 62,796 buffers + 1,813 temp -> 59-78ms / 46,260 buffers for a Limit=16 TV row; the two Latest shapes were 264s/day of DB time and sit behind every home-screen Latest row. Upstream bug, not multi-replica-specific | upstream rewrote this path (PR #16062 returns Season/Series containers, a different API result); drop when UPSTREAM_REF contains it and the clients are happy with the new shape |
| `0011-items-count-a-season-s-children-instead-of-materiali.patch` | `Season.GetItemsInternal` answers the `Limit=0` count shape (what `Folder.FillUserDataDtoValues` issues per Season DTO) with the repository count instead of fetching every episode of the whole series plus every user's UserData and filtering in memory. New `InternalItemsQuery.SeasonMembership` (SQL form of `FilterEpisodesBySeason`: `ParentIndexNumber = N` or `SeasonId` points at a same-key Season) and `HasAiredSeasonOverride` (a LIKE on the Data blob; any series carrying AirsBefore/After keeps the in-memory path, exact because Data omits nulls); `Folder.RequiresPostFiltering` becomes protected. That statement was 1.62M calls at 20.5ms, 55% of ALL DB time (the hourly cache-warm's two season passes = 1,434 calls/run). Measured worst case (1,022-episode series) 38ms / 12,292 buffers / 1,022 rows -> 12ms / 2,457 buffers / 1 row. Known ceilings: duplicate episode keys with per-copy Played state, and SQL parental filtering vs `BaseItem.IsVisible` (the gap Series counts already have); 18 seasons without a number and any series with relocated specials stay on the in-memory path | upstream stops materialising the series for a count (master's `Folder.FillUserDataDtoValues` moved to `ItemCountService` in PR #16062 but `Season.GetItemsInternal` still materialises for every other caller) |

Image-layer divergence (no server patch involved):

| Layer | What | Drop when |
|---|---|---|
| rffmpeg dispatch shims | [rffmpeg](https://github.com/joshuaboniface/rffmpeg) pinned by commit + checksum (no upstream releases), installed as `ffmpeg-dispatch`/`ffprobe-dispatch` with a baked `/etc/rffmpeg/rffmpeg.yml`; routes encodes to an ssh worker with local fallback | Jellyfin grows native remote transcoding |

Ceilings worth knowing:

- Single-node behavior is unchanged by construction: every gate defaults open when `JELLYFIN_ROLE` is unset, the skip-gate only acts when its env var is set, and the dispatch shims sit unused until the encoder path is pointed at them. A stock deployment of this image behaves like the official one.
- The image build compiles the server but keeps the official image's jellyfin-web and jellyfin-ffmpeg; a web or ffmpeg change upstream arrives via the base image bump, not this repo.
- The dispatch path is single-worker with local fallback, not worker HA: rffmpeg load-balances across registered hosts, but this repo's smoke only proves one worker plus fallback. Register more hosts if you need spread.
- Builds carry `-p:NoWarn=CA1707` until UPSTREAM_REF passes upstream's own rename of two migration class names (same story as the sibling plugin repo).
